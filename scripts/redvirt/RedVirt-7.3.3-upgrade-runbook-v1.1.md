# RED VIRT 7.3 → 7.3.3 — безопасное обновление хостов, версия сценария 1.1

> Для одного узла за один раз. Сначала апробация на выделенном хосте; не запускать параллельно на нескольких гипервизорах. Обязательно окно обслуживания, IPMI и подтверждённая резервная копия Hosted Engine/хранилищ.

## Что делаем вручную

Только три инфраструктурных действия при успешном прохождении проверок:

1. **Engine → Перевести хост в обслуживание (Maintenance)**, убедиться, что виртуальные машины эвакуированы. Не путать с `GLOBAL MAINTENANCE` Hosted Engine.
2. **Перезагрузить хост вручную** после сообщения `BOOT CHECK PASSED` / `UPGRADE ... PASS`. Наблюдать через IPMI.
3. **Engine → Включить (Activate)** после автоматического `postboot` и получения сети/ядра. Затем провести автоматическую `final`.

Подтверждение имени хоста в CLI перед DNF является защитой от случайной установки, не дополнительным инфраструктурным действием.

## Доставка скрипта на очередной хост

Скопировать `redvirt-upgrade-v1.1.sh` на гипервизор, затем на нём:

```bash
install -m 700 /path/to/redvirt-upgrade-v1.1.sh /root/redvirt-upgrade-v1.1.sh
bash -n /root/redvirt-upgrade-v1.1.sh
```

Никогда не копировать `/root/redvirt-upgrade/` **с другого хоста** — там хранятся уникальные PV, Multipath, IP и версия загрузочного ядра.

## Быстрый старт: скачивание с GitHub на очередной хост

Репозиторий: [Yury-Learn/All](https://github.com/Yury-Learn/All), ветка **main**, каталог [scripts/redvirt](https://github.com/Yury-Learn/All/tree/main/scripts/redvirt). Прямая ссылка на [Bash-скрипт](https://github.com/Yury-Learn/All/blob/main/scripts/redvirt/redvirt-upgrade-v1.1.sh).

Выполняйте от **root выбранного гипервизора**, пока он ещё `Up` и подключены все штатные хранилища:

```bash
cd /root
curl --fail --location --retry 2 --connect-timeout 15 --max-time 180 \
  'https://raw.githubusercontent.com/Yury-Learn/All/main/scripts/redvirt/redvirt-upgrade-v1.1.sh' \
  --output /root/redvirt-upgrade-v1.1.sh.download

test -s /root/redvirt-upgrade-v1.1.sh.download
bash -n /root/redvirt-upgrade-v1.1.sh.download
install -m 700 /root/redvirt-upgrade-v1.1.sh.download /root/redvirt-upgrade-v1.1.sh
rm -f /root/redvirt-upgrade-v1.1.sh.download

sha256sum /root/redvirt-upgrade-v1.1.sh
head -n 4 /root/redvirt-upgrade-v1.1.sh
```

Зафиксируйте SHA-256 скрипта в журнале работ: содержимое ветки `main` может впоследствии измениться. Не запускайте `curl URL | bash`. Если GitHub недоступен с гипервизора, скачайте скрипт на административную станцию и доставьте его по `scp`. Не меняйте ради скачивания DNS, firewall и маршруты рабочего сервера.

Отдельно можно сохранить эту инструкцию:

```bash
curl --fail --location \
  'https://raw.githubusercontent.com/Yury-Learn/All/main/scripts/redvirt/RedVirt-7.3.3-upgrade-runbook-v1.1.md' \
  -o /root/RedVirt-7.3.3-upgrade-runbook-v1.1.md
```

**Не загружайте в публичный репозиторий `All`** рабочие логи, снимки PV/iSCSI, внутренние IP-адреса, сертификаты и закрытые ключи.

## Контрольные правила перед началом

- Обновляется **один гипервизор за раз**. Каталог `/root/redvirt-upgrade/` содержит уникальные данные **данного хоста**.
- В Engine убедитесь, что хост имеет статус `Up`, есть согласованное окно обслуживания, доступен IPMI, подтверждены резервные копии и исправна управляющая ВМ Hosted Engine на другом узле. `GLOBAL MAINTENANCE` Hosted Engine — отдельный кластерный режим.
- Проверьте текущее ядро `uname -r`, свободное место `df -h /boot /var` и корректность времени `timedatectl status`: ошибка времени может нарушить проверку сертификатов.
- Нельзя повторно запускать `baseline` поверх существующего эталона, если `expected-pv-uuids.txt` уже создан. Не удаляйте эталон, чтобы «попробовать снова».
- Нулевой список ВМ в VDSM **не заменяет** режим `Maintenance` в Engine. Не подделывайте файлы-маркеры `PASS` и не обходитe проверки.


## Выполнение по этапам

### Отдельная проверка сертификатов и репозитория до обслуживания

```bash
bash /root/redvirt-upgrade-v1.1.sh certs
bash /root/redvirt-upgrade-v1.1.sh repo
```

- `certs` проверяет сроки действия сертификатов в `/etc/pki/vdsm` и доверие **VDSM host certificate** (`certs/vdsmcert.pem`) к `certs/cacert.pem`. При истечении в ближайшие **7 суток** сценарий останавливается, в ближайшие **30 суток** выдаёт предупреждение. **Это не проверка всех libvirt/SPICE/VNC-сертификатов**, видимых в Engine, и не перевыпуск. Отдельное действие в Engine **«Обновить информацию о сертификатах хоста»** лишь освежает сведения в интерфейсе.
- `repo` проверяет `virtualization-7.3-host-updates`, URL, `gpgcheck=1`, локальный GPG-ключ и доступность метаданных (три попытки). Успешное выполнение **не гарантирует**, что RPM-транзакция возможна без конфликтов, и не подтверждает криптографическую подпись самих метаданных; подпись RPM остаётся обязательной.
- В случае отказа репозитория начните с диагностики **без изменения сети**:

```bash
getent ahostsv4 repo.red-soft.ru
grep -R -n -A 14 '^\[virtualization-7.3-host-updates\]' /etc/yum.repos.d/*.repo
ip -4 route
```

При проблемах DNS, срока сертификата, ключа или URL не отключайте GPG и не используйте `--nogpgcheck` / `sslverify=0`. Не подменяйте репозиторий неподтверждённым зеркалом. На пилоте Graviton 3 DNS работал нестабильно; диагностика проводится по каждому серверу.


### 0. Пока хост работает в Engine (Up), ДО обслуживания

```bash
bash /root/redvirt-upgrade-v1.1.sh baseline
```

Скрипт снимет эталонные PV UUID, список путей для каждого Multipath WWID, конфигурацию сети, проверит версию и сертифицированную редакцию РЕД ОС, сертификаты VDSM (сроки и доверие к локальному CA) и `virtualization-7.3-host-updates` (ключ GPG и доступность метаданных). Также определит драйвер контроллера системного диска из sysfs текущего ядра. Если не смог определить — **STOP**, а не слепая установка.

### 1. РУЧНО: Engine → Обслуживание

Убедиться, что статус именно `Maintenance`, нет действующих ВМ, открыт доступ IPMI. Глобальное обслуживание Hosted Engine и правила его снятия управляются отдельно по согласованному плану. Скрипт не переводит хост в Maintenance и не проверяет Engine REST API; `--maintenance-confirmed` означает личное подтверждение оператора.

### 2. Установка автоматически внутри tmux

```bash
tmux new -s redvirt-upgrade
bash /root/redvirt-upgrade-v1.1.sh upgrade --maintenance-confirmed
```

Скрипт:

- Проверяет VDSM VM list = `[]` и отсутствие процессов QEMU; критические службы.
- Проверяет срок действия/цепочку VDSM-сертификата и доступность **только основного** host-updates-репозитория, с трёхкратной попыткой при нестабильном DNS.
- Применяет исключения для Certified: `*libvirt*`, `*libguestfs*`, `*qemu*`, `*grub2*`, `*shim*`, `redvirt-release`, `*capstone*`, `*virtiofsd*`.
- Загружает RPM через `dnf upgrade --downloadonly -y`; затем рассчитывает транзакцию из кэша (`--assumeno`) и запрещает неожиданные удаления/ошибки разрешения зависимостей.
- Требует **напечатать полное имя хоста**, затем выполняет `dnf --cacheonly upgrade -y` с одним репозиторием и включённым `gpgcheck=1`.
- Проверяет, что прежнее работающее ядро сохранилось; новый kernel и GRUB корректны; внутри *нового* initramfs присутствуют `lvm`, `dmsetup` (когда нужны), а также драйвер системного контроллера, обнаруженный в sysfs до обновления. Для встроенного драйвера допускает `=y` в конфигурации ядра. НЕ пересобирает initramfs автоматически.
- **Не перезагружает** машину и не изменяет настройки Engine, iSCSI, Multipath, NetworkManager, OVS, HA.

Возможно длительное скачивание RPM — на Graviton 3 774 МБ скачивались около часа из-за скорости репозитория.

**ВАЖНО**: при ошибке скрипт останавливается. Изменения пакетов до обнаруженной ошибки уже могли быть внесены: не перезагружать и не запускать всю команду повторно без проверки `dnf history` и лога.

### 3. РУЧНО: перезагрузка

Только после успешного выполнения `upgrade`, при доступном IPMI и без ВМ. Скрипт сам команду `reboot` никогда не вызывает.

### 4. После reboot — проверка до активации

```bash
bash /root/redvirt-upgrade-v1.1.sh postboot
```

Проверяет новое ядро, службы, IP-адреса относительно исходного состояния и сертификаты. Делает снимок LVM/Multipath/iSCSI. **Отсутствие части SAN-сессий и `partial` VG допускается до активации Engine, но явно отражается в отчёте.** Не включает автоматически `iscsi.service`, не выполняет `iscsiadm --loginall`, не активирует LV/VG.

### 5. РУЧНО: Engine → Включить

В пилоте после этой операции количество iSCSI-сессий выросло до 17, PRODUCT1 восстановил 4 пути, RESERVE1 — 2 пути; заработал HA-agent.

### 6. Финальная проверка

```bash
bash /root/redvirt-upgrade-v1.1.sh final
```

Обязательны все PV UUID из `baseline`, отсутствие `partial` LV/VG, сохранение всех исходных IPv4-адресов, **не меньше исправных путей для каждого WWID**, чем до обслуживания, не меньше iSCSI-сессий, чем было в эталоне, активные VDSM/libvirt/SAN/HA, доступность `hosted-engine --vm-status`. Состояние `Up` и домены `Active` дополнительно должны быть подтверждены в Engine.

## Дополнительные самостоятельные проверки

```bash
bash /root/redvirt-upgrade-v1.1.sh certs  # Проверка сертификатов, без перевыпуска
bash /root/redvirt-upgrade-v1.1.sh repo   # Доступность основного репозитория, без установки
```

`repo` обновляет только локальный DNF-кэш метаданных; при недоступности DNS останавливается, без изменений сетевых настроек. HTTP-репозиторий не защищает метаданные TLS, несмотря на включённый контроль подписи RPM. Устранение проблемы DNS/TLS — отдельная задача.

## Что необходимо учитывать

- Обновление DNF из CLI отличается от полной процедуры Engine: сертификаты и некоторые действия host-deploy вручную не имитируются. Сертификаты **только проверяются**.
- Конфигурация сети, драйвер загрузочного контроллера и способ загрузки могут отличаться на Lenovo/Graviton. При несовпадении скрипт прерывает операцию; не добавляйте драйверы в `initramfs` «на всякий случай».
- Операция `baseline` должна выполняться **до Maintenance**, чтобы эталон охватывал все активированные в Engine домены хранения. При ошибке получения эталона на очередном хосте не обходите проверку.
- У уже обновлённого `graviton3` имеется эталон старого скрипта версии 1.0, у которого нет файлов `baseline/ipv4.txt`, `baseline/path-counts.txt`, `boot-controller-modules.txt`. Не пытайтесь бездумно использовать его в новой процедуре, не удаляйте оригинальный эталон. Отдельные стадии `certs` и `repo` версии 1.1 можно проверить независимо.
- Для штатного сценария нужны только три ручные инфраструктурные операции, но возникновение проблем (например, сертификат истёк, репозиторий недоступен или загрузочный драйвер отсутствует) означает **STOP** и индивидуальное исправление, а не автоматическую попытку ремонта.
- Не отключайте `GLOBAL MAINTENANCE` Hosted Engine до завершения согласованного окна обслуживания; после работ восстановление HA должно быть выполнено отдельно согласно плану.
- Временная установка пакетов не откатывается автоматически, GRUB старого ядра не гарантирует совместимость со всем обновлённым пользовательским стеком.

## Контрольные точки: что означает PASS

| Этап | Что проверяется | Что этим ещё НЕ доказано |
|---|---|---|
| `certs` | Указанные VDSM-сертификаты и локальный CA | Полная проверка сертификатов в Engine и перевыпуск |
| `repo` | URL/GPG-настройки и получение метаданных | Успешность транзакции и совместимость обновлений |
| `baseline` | Сохранены исходные PV, WWID/пути, IPv4, boot-драйвер | Режим Maintenance или отсутствие ВМ |
| `upgrade` | DNF и проверки ядра/GRUB/`initramfs` | Реальная загрузка нового ядра и полноценная работа SAN |
| `postboot` | Новое ядро, базовые службы, IP, VDSM-сертификаты | Все SAN-пути до активации Engine |
| `final` | Исходные PV/пути/IP и состояние Hosted Engine HA | Состояние в UI Engine, запуск тестовой ВМ и допуск к нагрузке |

**Важно:** если `dnf check-update` не обнаружил новых пакетов с исключениями Certified, стадия `upgrade` сообщает `No updates available` и заканчивается **без** маркера `upgrade-completed`. Это не означает успешное обновление. `final` также может сообщить `FINAL PASS: BASELINE TEST ONLY`, если полный цикл не был зарегистрирован; только `FINAL PASS: UPGRADE VERIFIED` соответствует финалу после установки и reboot.

Проверка Multipath сравнивает исправные пути **отдельно по каждому WWID**, не суммарно. Отдельно сверяются PV UUID и число iSCSI-сессий. Совпадающее количество iSCSI-сессий не доказывает, что подключены те же самые порталы: при сомнении сравнивайте `baseline/iscsi.txt` с `final/iscsi.txt`.

## Проверка в Engine после активации

В меню **Виртуализация → Хосты** выберите гипервизор: статус должен стать **`Up`**, сведения о версиях ядра и VDSM — обновиться, связанные домены хранения — быть доступными. По потребности обновите **только информацию** о сертификатах и проверьте даты действия в интерфейсе.

`hosted-engine --vm-status` должен показывать хотя бы одну исправную управляющую ВМ Engine на одном из HA-хостов. У обновлённого хоста строка `Engine status: vm down` может быть нормальной, если управляющая ВМ работает на другом сервере; важно не путать локальный статус с кластерным.

Скрипт **не** запускает тестовую ВМ и не запрещает Engine распределять новые нагрузки после активации (`Up`). Допуск рабочих ВМ должен быть согласован отдельно. Не выключайте `GLOBAL MAINTENANCE` до конца утверждённого окна.

## Остановка и действия при ошибках

| Проблема | Безопасные действия |
|---|---|
| `certs`: истёк сертификат, не прошла цепочка | Остановить работу; проверить дату, issuer, CA; согласовать перевыпуск через Engine, не переписывать PEM вручную |
| `repo`: отсутствует URL/ключ, ошибка DNS | Проверить конфигурацию и сеть командами выше; не отключать GPG |
| `baseline`: отсутствует boot-драйвер или карты Multipath | **Не** переводить хост в обслуживание; исследовать оборудование и LUN отдельно |
| `upgrade`: остались ВМ | Прервать установку; завершить эвакуацию в Engine |
| `upgrade`: конфликт RPM/предложено удаление | Не продолжать; сохранить `offline-transaction-plan.txt` и журнал, отдельно разобрать зависимости |
| Ошибка **после DNF**, не пройдена проверка GRUB/`initramfs` | **Не перезагружать**. Сохранить `dnf history`, `rpm -q kernel-lt`, `grubby --default-kernel` и `lsinitrd`; восстановление планировать индивидуально |
| `postboot`: неправильное ядро, пропала сеть | **Не** нажимать «Включить»; диагностика через IPMI/консоль |
| `postboot`: частично отсутствуют SAN/LUN | До Engine Activate это возможно; при `POSTBOOT PASS` продолжить штатную активацию, но не запускать `iscsiadm --loginall` или `vgchange` |
| `final`: не хватает PV/путей/сеансов, проблема HA | Хост **не готов** к нагрузке, сравнить исходный снимок и Engine/VDSM/SAN |

Журналы текущего этапа:

```bash
ls -lt /root/redvirt-upgrade/logs/ | head
tail -n 100 /root/redvirt-upgrade/logs/final-*.log
```

Если ещё не было `final`, используйте лог соответствующей стадии (`baseline-*.log`, `upgrade-*.log`, `postboot-*.log`). Для наблюдения за установкой используйте уже открытую `tmux`-сессию; **не запускайте вторую транзакцию DNF**.

Не делайте `dnf history undo/rollback`, `vgchange -an`, `dmsetup remove`, переключение GRUB-default или массовый iSCSI-login без отдельно проверенного плана восстановления.

## Чек-лист закрытия одного сервера

- [ ] `baseline` снят до обслуживания при полном доступе к SAN
- [ ] Ручное действие 1: Engine → `Maintenance`, все ВМ эвакуированы
- [ ] `upgrade` завершён с проверкой GRUB и нового `initramfs`
- [ ] Ручное действие 2: перезагрузка; затем `postboot` прошёл
- [ ] Ручное действие 3: Engine → `Activate`, статус `Up`
- [ ] `final` вывел **`FINAL PASS: UPGRADE VERIFIED`**, все исходные PV/пути доступны
- [ ] Доступны домены хранения; сроки сертификатов в норме; Hosted Engine исправен
- [ ] Зафиксированы ядро, отложенные RPM (`capstone`/`virtiofsd`), журналы и допуск к нагрузкам


## Журналы

На каждом хосте: `/root/redvirt-upgrade/logs/`, плюс каталоги `/root/redvirt-upgrade/{baseline,pre-upgrade,post-install,postboot,final}/` и файлы сравнений.

Скрипт разработан для пилотного набора программ 2026-10-13. Он не заменяет резервное копирование, тестовые ВМ и процедуру согласования у РЕД СОФТ.
